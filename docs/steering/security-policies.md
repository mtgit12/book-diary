# Security Policies

## 基本方針

- 多層防御、最小権限、デフォルト拒否(判断できない場合は拒否する)。
- 外部入力は信用しない。ユーザーの入力に加えて、楽天ブックス API の応答とバッチからのデータも外部入力として扱う。
- 認証(誰か)は Sanctum、認可(何をしてよいか)は Policy で行う。

## 認証

- Web は Sanctum の SPA 認証(セッションクッキー + CSRF トークン)、バッチはバッチ専用の API トークン(ability を `batch` に限定)を使う。
- CORS と `SANCTUM_STATEFUL_DOMAINS` には、フロントのドメインだけを指定する。
- 状態を変える処理は POST、PUT、PATCH、DELETE だけで行う。
- セッションは操作がなければ120分で切れる。「ログイン状態を保持する」を選んだ場合は、30日間保持する。
- クッキーには `Secure`、`HttpOnly`、`SameSite=Lax` を付ける。
- ログイン時はセッション ID を再生成する。ログアウト時はセッションを破棄し、CSRF トークンを再生成する。
- パスワードは最低8文字とし、Laravel 標準のハッシュ化で保存する。
- メールアドレスの確認を必須にする。確認していないユーザーは機能を使えない。
- ログインの試行回数は、メールアドレスと IP の組み合わせごとに制限する(1分に5回)。
- パスワード再設定の応答は、メールアドレスが登録されているかどうかにかかわらず同じにする。
- パスワードの変更と退会の前には、現在のパスワードを再入力してもらう。
- 内部 API は専用のルートグループにまとめ、バッチ用のトークン以外では呼べないようにする。

## 認可

- 認可は Policy に集約し、Controller で確認する。
- ユーザーが扱えるのは自分のデータだけとする。Repository の検索は必ず `user_id` で絞り込む。
- ほかのユーザーのリソースへのアクセスには 404 を返す。
- 所有者はリクエストの内容ではなく、ログイン中のユーザーから決める。

## 入力の検証

- フロント(zod)とバックエンド(FormRequest)の両方で検証し、最終的な判断はバックエンドで行う。
- 許可する値を列挙する方式(allow-list)を使う。読書状態、キーワードの種別、並び替えの項目が対象。
- すべての文字列に最大長を設け、一覧の取得件数にも上限を設ける。
- モデルの `$fillable` を明示し、Service には検証済みの値(`validated()`)だけを渡す。
- 追跡キーワードは、1ユーザーあたりの登録件数に上限を設ける。
- ログイン後の遷移先は、アプリ内の相対パスだけを許可する。
- エラー応答には、SQL やスタックトレースなどの内部の情報を含めない。

## 出力のエスケープ

- HTML は React の標準のエスケープに任せ、`dangerouslySetInnerHTML` は使わない。
- 感想メモはプレーンテキストとして扱い、HTML や Markdown として解釈しない。
- 外部の URL(商品ページ、書影)は、`https:` のものだけを表示する。
- 外部へのリンクには `rel="noopener noreferrer"` を付ける。
- SQL は Eloquent とクエリビルダーのバインディングを使い、入力を Raw 系のメソッドに埋め込まない。

## 外部 API

- 楽天ブックス API を呼ぶのはバックエンドとバッチだけとし、認証情報はサーバーの環境変数で持つ。
- 応答の型と長さを確認してから保存し、タイムアウトとリトライの上限を設定する。
- 検索 API にはユーザーごとのレート制限を設ける。

## シークレット

- シークレットはコミットしない。`.env.example` には、キーの名前とダミーの値だけを書く。
- 本番のシークレットは GitHub の Environments のシークレットで管理し、デプロイ時にサーバーの `.env` を生成する(パーミッションは `600`)。
- 本番では `APP_DEBUG=false` にする。
- `NEXT_PUBLIC_` から始まる環境変数には、公開してよい値だけを入れる。
- 必須の環境変数が足りない場合は、起動時にエラーにする。
- 漏えいの疑いがあれば、すぐに再発行して古い値を無効にする。

## 個人データ

- 収集するのは、メールアドレス、表示名、パスワードのハッシュ、読書記録だけとする。
- API の応答は API Resource で返す項目を明示し、パスワードやトークンを含めない。
- 退会したら、ユーザーと関連データ(本棚、感想メモ、追跡キーワード、トークン)をすぐに完全に削除する。

## ログ

- 認証の成功・失敗、試行回数の制限、パスワードの変更・再設定、退会、認可の拒否を記録する。
- パスワード、トークン、セッション ID、API キー、リクエストボディの全体はログに出さない。
- ユーザーはユーザー ID で記録し、リクエスト ID でログを照合できるようにする。

## 通信・ヘッダー

- すべての通信を HTTPS にし、HSTS を有効にする。
- CSP、`X-Content-Type-Options`、`X-Frame-Options`(または `frame-ancestors`)、`Referrer-Policy` を設定する。
- 公開するポートは 80 と 443 だけにし、DB は外部に公開しない。SSH は鍵認証にし、接続元の IP を限定する。

## 脆弱性対策

- lock ファイルを Git に含め、依存関係は Dependabot で更新する。
- CI で `composer audit` と `bun audit` を実行する。
- GitHub の Secret scanning と push protection を有効にする。
- 次の項目をテストで確認する。
  - 未ログインで 401 になること
  - ほかのユーザーのリソースで 404 になること
  - バッチ用以外のトークンで内部 API を呼べないこと
  - ログインの試行回数の制限が働くこと
  - メールアドレスを確認していないユーザーが機能を使えないこと
- 新しい API を追加するときは、認証、認可、バリデーション、レート制限、返す項目をレビューで確認する。
