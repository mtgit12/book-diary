# 概要

テストの種類、書き方、モックの方針、カバレッジの考え方を定める。機能ごとのテストの対象は、機能の決定後に追記する。

## 基本方針

- 実装の内部ではなく、利用者から見た振る舞いをテストする。
- 外部への通信(外部 API、メール送信)は、テストで実際には行わない。それ以外は、なるべく本物を使う。
- 不具合を直すときは、先にその不具合を再現するテストを書く。

## テストの種類

| 種類 | ツール | 置き場所 | 対象 |
|---|---|---|---|
| バックエンドの単体テスト | Pest | `backend/tests/Unit/` | Service のビジネスロジックなど |
| バックエンドの Feature テスト | Pest | `backend/tests/Feature/` | API のエンドポイント(HTTP のリクエストから DB まで) |
| フロントの単体テスト | Vitest + Testing Library | `frontend/tests/`(`src/` と同じ構成) | コンポーネント、フック、ユーティリティ、zod のスキーマ |
| E2E テスト | Playwright | `frontend/e2e/` | 主要な利用の流れ |
| バッチのテスト | Go 標準の `testing` | 対象と同じパッケージ(`*_test.go`) | バッチの処理 |

- テストの中心は Feature テストとする。単体テストは、条件分岐の多いロジックに絞る。
- E2E テストは、画面をまたぐ流れだけを確かめる。入力の組み合わせなどの細かい確認は、単体テストや Feature テストで行う。

## 書き方

- テストの名前は、何を確かめるかが日本語でわかるように書く(例: 「ほかのユーザーのリソースは404になる」)。
- 1つのテストでは1つの振る舞いだけを確かめ、準備、実行、確認の順に書く。
- テスト同士は独立させ、実行順に依存させない。
- 日時に依存する処理は、時刻を固定してテストする。

## バックエンド(Pest)

- テスト用の DB は MySQL を使う。開発用とは別の DB を用意し、`RefreshDatabase` で毎回初期化する。
- テストデータは Factory で作り、テストに関係する値だけを明示的に指定する。
- 認証済みのリクエストは `Sanctum::actingAs()` で作る。
- 外部への通信は、次のように扱う。
  - 外部 API は `Http::fake()` で応答を固定する。
  - `Http::preventStrayRequests()` で、意図しない通信を失敗させる。
  - メールと通知は `Mail::fake()`、`Notification::fake()` で送信を確認する。
- Feature テストでは Service や Repository をモックしない。
- Service の単体テストでは、Repository のインターフェースをモックする。
- アサーションは、HTTP のレスポンスには `assertStatus` や `assertJson` などのメソッドを使い、値の確認には `expect()` を使う。

## フロントエンド(Vitest + Testing Library)

- 要素は、利用者から見える情報で探す。優先順位は `getByRole`、`getByLabelText`、`getByText` の順とし、`data-testid` は最後の手段とする。
- 操作は `userEvent` で再現する。
- API の応答は、`vi.mock` で共通 API クライアント(`@/lib/api-client`)をモックして固定する。
  - 各機能の `api/` にある関数は、同じファイルのフックから呼ばれる。同じファイル内の呼び出しは `vi.mock` で差し替えられないため、API の関数ではなく共通 API クライアントをモックする。
- TanStack Query を使うコンポーネントは、テストごとに新しい `QueryClient`(リトライなし)で包んで描画する。描画用の共通の関数は `tests/` に置く。
- zustand のストアは、テストごとに初期状態に戻す。
- 非同期の Server Components と `.server.ts` は Vitest で扱いにくいため、E2E テストで確かめる。

## E2E テスト(Playwright)

- Docker Compose で Next.js、Laravel、MySQL を起動し、本物の API に接続して実行する。
- 外部 API は呼ばない。E2E 用の環境では、固定の応答を返す実装に切り替える。
- テストの前に、シーダーで DB を初期化する。
- 対象とする流れは、機能の決定後に決める。
- 待ち合わせには、Playwright の自動待機と `expect` を使う。決まった時間だけ待つ処理(`waitForTimeout`)は使わない。

## バッチ(Go)

- 複数の入力パターンは、テーブル駆動テストでまとめる。
- 外部 API と内部 API は `httptest` のサーバーで置き換える。

## カバレッジ

- カバレッジは CI で計測して表示する。数値でマージを止めることはしない。
- 数値の目標の代わりに、次の項目は必ずテストする。機能ごとの項目は、機能の決定後に追記する。
  - すべての API の、正常系と主な異常系(401、404、422)
  - 認証と認可(ほかのユーザーのデータを扱えないこと)
  - Service の条件分岐
  - フロントのフォームのバリデーションと、エラーの表示

## CI

- プルリクエストごとに、すべてのテスト(E2E を含む)を実行する。
- 失敗するテストがある状態ではマージしない。不安定なテストは放置せず、原因を直す。

## アンチパターン

| 避けること | 代わりにすること |
|---|---|
| private メソッドや内部の state を直接テストする | 公開されている振る舞いを通してテストする |
| Feature テストで Service や Repository をモックする | 本物の DB を使って API を通しで確かめる |
| テストで本物の外部 API を呼ぶ | `Http::fake()` や `httptest` で応答を固定する |
| 1つのテストで複数の振る舞いを確かめる | テストを分ける |
| ほかのテストが作ったデータに依存する | テストごとにデータを用意する |
| スナップショットテストで画面全体を固定する | 確かめたい要素を個別に確認する |
