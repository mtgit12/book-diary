# API Standards

## 基本方針

- リソースを中心に設計し、URL とメソッドから処理の内容がわかるようにする。
- 既存のクライアントを壊す変更は避ける。
- 認証と認可を先に確認し、それからビジネスロジックを実行する。

## エンドポイント

- 形式は `/api/v1/{resource}[/{id}][/{sub-resource}]` とする。
- リソース名は kebab-case の複数形の名詞とし、動詞は使わない。
- ネストは1階層までにする。
- 例:
  - `/api/v1/bookshelf-items`
  - `/api/v1/bookshelf-items/{id}`
  - `/api/v1/tracking-keywords`
  - `/api/v1/new-releases`
- 「この著者を追う」などの操作も、リソースの作成として表す(`POST /api/v1/tracking-keywords`)。
- バッチ用の内部 API は `/api/v1/internal/` の下に置く。

## HTTP メソッド

| メソッド | 用途 |
|---|---|
| GET | 取得。状態を変えない |
| POST | 作成 |
| PUT | 更新 |
| DELETE | 削除 |

## リクエスト

- ヘッダーには `Accept: application/json` と `Content-Type: application/json` を付ける。
- ボディは JSON のオブジェクトをそのまま送る。`data` で包まない。
- キーは snake_case とする。
- 日付は `YYYY-MM-DD`、日時は ISO 8601(タイムゾーン付き)で表す。

```json
{ "status": "reading", "memo": "3巻まで読んだ" }
```

## レスポンス

- 単一のリソースは API Resource で `data` に包んで返す。
- 値がない項目は、キーを省略せずに `null` を返す。

```json
{
  "data": {
    "id": 12,
    "status": "reading",
    "memo": "3巻まで読んだ",
    "created_at": "2026-10-23T10:00:00+09:00"
  }
}
```

- 一覧は Laravel のページネーションの形式(`data`、`links`、`meta`)で返す。

```json
{
  "data": [{ "id": 12, "status": "reading" }],
  "links": { "first": "...", "last": "...", "prev": null, "next": "..." },
  "meta": { "current_page": 1, "last_page": 5, "per_page": 20, "total": 93 }
}
```

## エラー

- Laravel 標準の形式で返す。
  - バリデーションエラーは `message` と、項目ごとのメッセージ(`errors`)を返す。
  - それ以外のエラーは `message` だけを返す。
- フロントはエラーの種類をステータスコードで判断する。`message` の文言で処理を分けない。
- スタックトレースや SQL などの内部の情報は返さない。

```json
{
  "message": "メモは1000文字以内で入力してください。",
  "errors": { "memo": ["メモは1000文字以内で入力してください。"] }
}
```

## ステータスコード

| コード | 使う場面 |
|---|---|
| 200 | 取得・更新に成功した |
| 201 | 作成に成功した(作成したリソースを返す) |
| 204 | 削除・ログアウトに成功した(ボディなし) |
| 401 | 未ログイン、またはトークンが無効 |
| 403 | 権限がない、またはメールアドレスを確認していない |
| 404 | リソースが存在しない、またはほかのユーザーのリソース |
| 419 | CSRF トークンが無効、またはセッションが切れた |
| 422 | バリデーションエラー(重複の登録を含む) |
| 429 | レート制限を超えた |
| 500 | サーバーの内部エラー |
| 503 | メンテナンス中、または外部 API が利用できない |

## 認証

- **Web(SPA 認証)**: 次の順で処理する。
  1. `GET /sanctum/csrf-cookie` で CSRF トークンを受け取る。
  2. ログイン API を呼ぶ。以降はセッションクッキーで認証する。
  3. 状態を変えるリクエストには `X-XSRF-TOKEN` ヘッダーを付ける(共通 API クライアントで処理する)。
- **バッチ**: `Authorization: Bearer {token}` ヘッダーでバッチ専用のトークンを送る。
- 認証が必要なルートには `auth:sanctum` を付ける。認証していないリクエストは、ビジネスロジックの前に 401 で拒否する。

## 一覧の取得

- ページネーションはページ番号方式とし、パラメーターは `page` と `per_page` とする。`per_page` は初期値を20件、上限を100件にする。
- 絞り込みは、項目ごとのクエリパラメーターで指定する(例: `?status=reading&author=...`)。
- 並び替えは、対象のカラムを `sort`、順序を `order`(`asc` または `desc`)で指定する(例: `?sort=sales_date&order=desc`)。
- 絞り込みと並び替えに使える項目は、エンドポイントごとに許可したものだけとする。

## バージョニング

- バージョンは URL(`/api/v1/`)で表す。
- 既存のクライアントを壊す変更は、新しいバージョンで行う。対象は次の変更。
  - 項目の削除や名前の変更
  - 型の変更
  - 必須のパラメーターの追加
- 項目や任意のパラメーターの追加は、同じバージョンで行う。
- 新しいバージョンを出したあとも、モバイルアプリなどの既存のクライアントが移行するまでは、古いバージョンを残す。
